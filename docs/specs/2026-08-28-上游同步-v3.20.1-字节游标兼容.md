# [TECHNICAL SPECIFICATION] 上游同步 v3.19.1 → v3.20.1：字节游标兼容、Pi 跟进、定价 9 条

## 1. 变更背景

cc-switch 上游积压 123 个提交（v3.19.1 → v3.20.1，后者 2026-08-28 当日发布），schema 从 v16 迁到 **v18**。
其中一条改动会**直接破坏本 App 的只读叠加层**。

### 1.1 P0：`last_line_offset` 被上游写死 0

上游 `session_usage.rs:710`（Claude 路径唯一写入点）：

```rust
/// 写入 Claude 路径的字节游标。`last_line_offset` 固定写 0：字节游标语义
/// 下行号不再维护，置 0 明确表示「行号游标不可用」。
"INSERT OR REPLACE INTO session_log_sync
     (file_path, last_modified, last_line_offset, last_synced_at,
      last_byte_offset, last_tail_fingerprint)
 VALUES (?1, ?2, 0, ?3, ?4, ?5)"        // ← 第三个占位是字面量 0
```

`SessionOverlay.loadSyncTable` 正是读 `last_line_offset`。故障链：

```
用户升级 cc-switch → 扫描一轮 → 该文件 last_line_offset 被覆盖为 0
→ 文件之后又被追加（活跃会话必然）→ mtime 门放行 → 我们读到 offset=0
→ 从第 0 行重解析整个文件
   ├ 30 天内的行：request_id 命中 proxy_request_logs → pruneRowsAlreadyInDB 剔除  ✅
   └ 30 天外的行：明细已被 rollup_and_prune 删除、request_id 失明
                  → 当作「待入库」叠加 → 与 usage_daily_rollups 已有成本双算  ❌
```

上游在 `sync_single_file` 文档注释里点名同一风险（「重导会在下次 rollup 时二次累加、永久放大统计」），
它靠字节游标规避；本 App 若不跟进即落入该陷阱。

## 3. 设计方案

### 3.1 游标模型：三态并存

升级后 `session_log_sync` 会长期存在两种行（未变化的文件因 mtime 门提前返回，**不写游标**，
长期停留在旧状态），加上用户尚未升级的旧库，共三态：

| 态 | 触发条件 | `last_byte_offset` | `last_line_offset` |
|---|---|---|---|
| **A** 旧库 | 用户 DB 仍是 v16/v17（无该列） | 列不存在 | 真实行数 |
| **B** 已升级未重扫 | v18 迁移后该文件还没被扫过 | `NULL` | 真实行数 |
| **C** 新版写过 | v18 且已扫过一轮 | 真实字节位（**可能合法地等于 0**） | 恒 `0` |

判定规则：

```
列不存在        → 行号路径（A）
列存在且 IS NULL → 行号路径（B）
列存在且非 NULL  → 字节路径（C），忽略 last_line_offset
```

**红线：绝不可写 `COALESCE(last_byte_offset, 0)`** —— 0 是 C 态的合法字节位，
用 COALESCE 会把 B 态误判成「从头读」，正是要防的双算。必须用
`sqlite3_column_type(...) == SQLITE_NULL` 区分。

### 3.2 关键伪代码

```swift
struct SyncCursor {
    var lastModified: Int64
    var lineOffset: Int64      // 仅 byteOffset == nil 时有效
    var byteOffset: Int64?     // nil = 行号游标（A/B 态）
}

// 列探测一次即可（连接级），SQL 按结果构造
private func loadSyncTable(_ db) -> [String: SyncCursor] {
    let hasByteCol = columnExists(db, "session_log_sync", "last_byte_offset")
    let sql = hasByteCol
        ? "SELECT file_path, last_modified, last_line_offset, last_byte_offset FROM session_log_sync"
        : "SELECT file_path, last_modified, last_line_offset, NULL FROM session_log_sync"
    // 第 4 列 sqlite3_column_type == SQLITE_NULL → byteOffset = nil
}

// 起点决策
if let m = marks[path], m.matchesDBCursor(dbState), m.bytesRead <= st.size {
    startBytes = m.bytesRead; linesRead = m.linesRead; skipLines = 0   // 进程内续读（不变）
    if m.mtimeNs == st.mtimeNs { return }
} else if let b = dbState.byteOffset {
    // C 态：直接 seek。越界（外部截断/重写）时钳到 EOF —— 对齐上游
    // 「游标钉至 EOF、不重放旧区间」，绝不回退到 0 重扫（那正是双算源头）
    startBytes = min(max(0, b), st.size)
    skipLines = 0
} else {
    startBytes = 0; skipLines = dbState.lineOffset                     // A/B 态：旧行号路径
}
```

`FileMark.dbOffset: Int64` 随之改为可同时表达两种游标的形态，
「db 游标是否推进」的判断改为整体比较（行号与字节位都要比）。

### 3.3 刻意不做的

- **不实现尾部指纹校验**：指纹是上游为「不重放已被 rollup 剪掉的区间」设的写侧保护。
  本 App 只读、以 `rows[requestId]` 字典去重、且每轮 `pruneRowsAlreadyInDB`，
  重放不会双算；越界钳到 EOF 已覆盖截断场景。
- **不读 `session_usage_dedup`**：Pi 专用（已核实）。判断某条 Claude 记录是否已入库，
  唯一依据仍是 `proxy_request_logs.request_id = 'session:' || <message.id>`。
- **不改 `effectiveUsageFilterL`**：上游白名单未纳入 `pi_session`。

## 4. 测试用例规划

新增 `Tests/SyncCursorCompatTests.swift`：

1. **A 态**：夹具库无 `last_byte_offset` 列 → 按 `last_line_offset` 跳行，行为与改动前逐字节一致（回归保护）
2. **B 态**：有列但值为 `NULL` → 仍走行号路径（**杀 COALESCE 变异体**）
3. **C 态**：`last_byte_offset = B` → 从字节 B 续读，`last_line_offset = 0` 被忽略（**杀「仍读行号」变异体**）
4. **C 态且 byteOffset = 0**：合法零字节位，必须整文件解析，不可当成 NULL（**杀 COALESCE 变异体**）
5. **越界钳制**：`byteOffset > fileSize`（外部截断）→ 钳到 EOF、本轮零产出，**不得回退到 0 重扫**（**杀「越界回退全量」变异体**）
6. **游标切换**：同一文件先 A 态扫描、再模拟 cc-switch 升级改写为 C 态 → 不得重复产出已消化区间的行

验证手法沿用既有约定：
- **变异测试**：每条用例注释写明它负责杀哪个变异体，逐个把生产代码改坏验证用例确实会挂
- **冻结库新旧对拍**：真实 db 快照 + 空 overlay，`swiftc -O` 分别编译 HEAD 与工作区，
  dump 汇总/按 app/Provider/Model/按来源/日志/走势后 diff，要求逐字节一致
  （本轮 DB 仍是 v16 = A 态，对拍即证明旧路径零回归）
