## 4. 跨源去重认 Codex 的请求模型别名（#7643，v4.0.25）

### 根因
- Codex 会话日志记的是客户端填的模型别名，代理行的 `model` 是路由映射后的上游模型，两边对不上 → 同一笔请求既算代理行又算会话行。上游在去重的模型匹配里加了一支：会话行是 Codex（`app_type = 'codex'` 且来源 `codex_session`）时，代理行的 `request_model` 非空、不是 `unknown`、去空白不分大小写后等于会话行的模型，也算同一笔。
- 我们的 `effectiveUsageFilterL` 是上游 `effective_usage_log_filter` 的逐字移植，缺这一支。

### 前人意图
- 模型匹配原来只有三支（相等 / 任一侧是 `unknown`），是照当时的上游写的；没有理由不跟。
- 过滤器按库的 schema 生成（`hasSemantics`）：旧库缺列时照写会在 prepare 阶段失败，所有读路径一起挂。`request_model` 同理，缺列就省掉这一支。

### 改法
- `effectiveUsageFilterL(hasSemantics:hasRequestModel:)`：模型匹配换成上游 `session_proxy_model_match_sql` 的四支；`effectiveUsageFilter(db)` 多探一次 `request_model` 列。
- 上游的 `effective_usage_log_filter_for_range` 只是同一语义的另一种写法（先数两类行、挑便宜的 SQL），我们全程用 `EXISTS` 写法，语义相同，不移植。

## 7. 菜单栏刷新开销

### 现象
- v2.4.1 进程连续运行 8 天，累计 CPU 时间折合平均约 2.4% 个核；内存 170 MB 上下。

### 根因（全量数据基准 + 采样）
菜单栏每个刷新 tick（默认 5 秒）跑一轮 `MenuBarDataLoader.load`。cc-switch 长期不入库时，待入库的叠加行有上万条、会话文件上千个，一轮的开销分三块：

1. **路径字符串走慢路径**（约占一半）。`ClaudeSessionFiles.join` / `OmpSessionFiles.entries` 用 `NSString.appendingPathComponent` 拼路径，得到的是桥接的 Cocoa 字符串（`NSPathStore2`）。这些路径是 `marks` / `sync` / `files` 几个字典的键，每轮每个文件要查好几次；桥接字符串的哈希和比较不走 UTF-8 快路径（采样里是 `_stringCompareSlow`、`_normalizedHash`、`-[NSPathStore2 characterAtIndex:]`）。
   调用链：`MenuBarDataLoader.load` → `UsageStore.snapshot` → `summaryLogsOnly` → `overlayRows` → `SessionOverlay.pendingRows` → `refreshLocked` → `nothingChangedLocked`（每个文件 `sync[path]`、`marks[path]`）；有文件在写时再加 `seenPaths.insert`、`scanFileLocked`、`Set(marks.keys).subtracting`。
2. **每条查询都整份拷贝叠加行**。`pendingRows` 每次返回 `Array(rows.values)`；一轮刷新有 6 条查询要叠加行（今日汇总、走势、最后活动时间、近 7 天、近 30 天、每个勾选的应用码片）。
3. **每条查询都重新合并去重**。`UsageStore.overlayRows` 每次把两个来源的行并起来：给第一个来源的全部 request_id 建 `Set`，过滤第二个来源，再拼成新数组。

复现证据（同一份全量数据的克隆，每拍之间睡过 2 秒节流窗口；CPU 毫秒，中位数）：

| | 会话扫描 | OMP 扫描 | 6 条查询 | 一轮合计 |
|---|---|---|---|---|
| 改前，无文件变化 | 50 | 5.7 | 48 | 116 |
| 改前，每拍有一个文件在写 | 127 | 5.0 | 43 | 181 |

只把路径换成原生字符串（实验）：会话扫描降到原来的五分之一上下。再加行快照与合并缓存，6 条查询里叠加行那部分降到 1 ms 以内。最终数字见「实施结果」。

### 前人意图
- `appendingPathComponent`：处理目录末尾的 `/`，拼出来的路径和 cc-switch 记在 `session_log_sync.file_path` 里的逐字相同（游标按路径查）。保留它，只把结果转成原生存储，内容不变。
- `pendingRows` 返回数组副本：调用方拿到的是不受后续扫描影响的一份。快照是不可变数组，语义相同。
- `overlayRows` 里按 request_id 去重：两个来源的命名空间不同，本来撞不上，留着兜底。合并规则原样保留（先到先得；累计结果为空时直接用下一个来源、不去重）。
- 2 秒节流（`minRefreshInterval`）：一轮刷新里多条查询共享一次扫描。不动。

### 模块设计
| 模块 | 职责 | 对外接口 | 依赖 |
|---|---|---|---|
| `Overlay/ClaudeSessionFiles`、`Overlay/OmpSessionFiles` | 会话文件发现 | 不变；产出的路径改为原生（连续 UTF-8）字符串 | Foundation |
| `Overlay/SessionOverlay`、`Overlay/OmpOverlay` | 各自的待入库行 | `pendingRows(db:)` 不变；行没变时返回同一份数组（写时复制，不拷贝元素） | OverlayDB / PricingTable 等，不变 |
| `Overlay/PendingRowsMerger`（新增） | 把各来源的待入库行并成一份（按 request_id 去重），来源没变时复用上次的结果 | `init(_ sources:)`、`rows(db:) -> [OverlayRow]` | 只依赖 `PendingUsageSource` 协议 |
| `Usage/UsageStore` | 查询 | 公开接口不变；`overlayRows` 改为「取合并结果 → 按条件过滤」 | → `PendingRowsMerger` |

依赖方向不变：App → Usage → Overlay → Pricing，无环。

- **行快照**：两个叠加层的 `rows` 字典加 `didSet { snapshot = nil }`，`pendingRows` 返回 `snapshot`（没有就从字典现做一份并记下）。任何一处改 `rows` 都会让快照失效，不靠人记；返回的内容恒等于当时的 `Array(rows.values)`，顺序也相同（浮点累加顺序不变）。
- **合并缓存**：`PendingRowsMerger` 记住上一次各来源返回的数组和合并结果；这一次各来源返回的数组与上次是同一块存储（基址和长度相同）就直接复用。缓存一直持有上一次的数组，所以同一基址只可能是同一块存储，且它不可能被原地改写（有第二个引用，写时会复制）——判断是可靠的。来源每次都返回新数组（测试替身）时永远不命中，退回到每次重新合并，结果仍然正确。
- 不做的：每轮只在水位变化时才全量剔除已入库行（省约 4 ms）、一轮刷新共用一个只读连接（每次建连要灌兜底定价表约 2.5 ms × 4）。收益小、要新增状态或公开接口，先不做。

## 爆炸半径
- 定价表：`ModelPricing.table` 被查询层（TEMP 兜底表）和两个叠加层（`PricingTable.find` 的最后一级）使用；只增不改。
- `pricingCandidates`：`ModelPricing.lookup`、`PricingTable.find`、`seedResolvedAliases`。只对一个确切的 id 多产出一个候选。
- `effectiveUsageFilter(db)`：所有读明细的路径（汇总、按 app、走势、三个页签、最早日期、按来源）。本机库没有代理行，结果不变；有代理行且 Codex 模型被映射过的库会少算重复的那部分。
- `providerNameSQL`：供应商统计的展示名与 provider 筛选。
- MBApp：`MenuBarDataLoader`、`MenuBarLabel`、`MenuBarSettingsView`、`PanelModel` 都按 `allCases` / `settingsOrder` 泛化处理。
- `overlayRows`：UsageStore 的全部查询。合并规则、过滤条件、行顺序都不变。
- `pendingRows`：UsageStore（经合并器）、`Tools/dump`、测试。
- 主窗口：只换前端产物 `Sources/App/web-panel/index.html`，桥接契约不动。

- **MBApp**：顺序、标题、展开键、额度说明四个现有用例先改期望值（红）再改实现。
- **刷新开销**：
  - 发现出来的路径 `isContiguousUTF8`（Claude、OMP 各一个用例，改前红）。
  - 两个叠加层：没有变化时连续两次 `pendingRows` 返回同一块存储；有变化后内容更新且与字典一致（改前红）。
  - `PendingRowsMerger`：合并规则与原实现逐条相同（多来源、重复 id、空来源在前、来源内部的重复不动）；来源没变时不重新合并（返回同一块存储）；任一来源换了数组就重新合并。
  - 结果不变：冻结库对拍 `matrix` / `overlay` / `replay` 与改前逐字节相同。
