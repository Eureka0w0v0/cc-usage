## 设计要点

### 1. Claude 1 小时缓存写入按 1.6 倍计（#7653）
- Anthropic 把缓存写入分成 5 分钟档（输入价 × 1.25）和 1 小时档（输入价 × 2），拆分记在 `usage.cache_creation.ephemeral_{5m,1h}_input_tokens`。定价表的 cache_creation 单价是 5 分钟档；上游从 v4.0.7 起把 1 小时那部分按这个单价的 1.6 倍计（`calculator.rs`：先 `min(1h, 总写入)`，再 `(总写入 − 1h + 1h × 1.6) × 单价`）。Claude Code 主会话默认用 1 小时缓存，差额不小。
- 拆分不落库。库里的行要么已按导入时的口径算好成本，要么成本为 0、由 `costSQL` 兜底（上游 backfill 同样只能按 5 分钟价）。所以只改 SessionOverlay 的现场定价，`costSQL` 不动。
- **开关跟着本机 CC Switch 的版本走**。叠加行迟早会被 cc-switch 补录的行替换，现场算的数必须和补录的一致，否则一打开 cc-switch 数字就跳：
  - ≥ 4.0.7 → 拆分计价；更早的版本（3.20.x 等）→ 不拆分；没装、或版本号认不出 → 拆分（没有补录方要对齐，按正确价）。
  - 版本号每次现读 `/Applications` 或 `~/Applications` 下的 `CC Switch.app/Contents/Info.plist`。升级是原地替换 .app，`Bundle(url:)` 按路径缓存实例，会一直报旧版本（用例 + 变异体钉住）。
  - 按数字逐段比较（按字符串比，`4.0.12` 会排在 `4.0.7` 前面）；只认开头的数字和点，`4.0.7-beta.1` 视为 4.0.7。
- 口径随定价一起按 TTL（5 分钟）重判。翻转时（多半是 CC Switch 刚升级）清空已叠加的行和续读进度，本轮从 cc-switch 的游标处整体重扫：已叠加的行是按旧口径定的价，不清空就会新旧混算。重判挂在「有变化才真扫」的预检之后，文件和库都没动时不重判，下一次有新用量或 cc-switch 补录时生效。
- 测试注入点：`SessionOverlay.init` 新增 `pricingTTL`、`ccSwitchVersion`（默认读本机）。

### 2. 跨源去重：legacy Codex 代理行（#7635 读侧）
- v4.0.7 起 Codex 会话导入会记 `cache_write_input_tokens`（按 total 语义存）。v3.17.0 之前的代理行（`input_token_semantics = 0`）从不记 Codex 缓存写入，恒为 0；新导入的会话行写入量大于 0，与它的指纹对不上，同一笔请求被算两次。上游在 `effective_usage_log_filter`（和 `_for_range`）里加了第三个分支：代理行写入量为 0、是 legacy 语义、会话行来自 `codex_session` 时，放行任意写入量。
- 本仓库逐字跟进。这个分支要读 `input_token_semantics`；旧库（schema < 13）没有这一列，照写会在 prepare 阶段报错、所有读路径一起挂。所以过滤改为按 schema 生成，缺列时省掉这个分支。省掉不改变结果：旧库里的 Codex 会话行由旧导入器写入，写入量恒为 0，已被第二个分支放行。
- 读路径统一经 `effectiveUsageFilter(db)`：`logConds` / `statsWhere` 的签名带上 db，其余 4 处直接引用一并替换。这一步单独跑过全量测试，旧用例全绿。

### 3. Provider 行身份 = (providerId, appType)（#8032）
- 「Claude」筛选折叠了 claude-desktop。同一个供应商在 Claude Code 和 Claude Desktop 都配过时，`GROUP BY provider_id, app_type` 会回来两行 id、名字都一样的记录；表格按 id 作 React key，重复 key 让切换应用后留下旧的行。上游在结果里加 `appType`，表格 key 改为 `[appType, providerId]`。
- Swift：`ProviderStatRow` 加 `appType`（SQL 读 `l.app_type`）。overlay 行改按 (providerId, appType) 分组、只并进同一身份的库内行，和库内行用同一套身份。原先只按 id 分组，同一个 OMP provider 打两家模型时会被并成一行。
- embed：钉住的 3.x `ProviderStatsTable` 只拿 providerId 当 key，又不能改上游文件，所以在 provider-stats 查询的默认值里挂 `select`，把 providerId 换成同样的组合键。3.x 的表格和来源下拉都不显示 providerId（下拉只用 providerName），换掉不影响展示。TanStack 对同一个 key 再调 `setQueryDefaults` 会整体替换，`select` 必须和 `keepPreviousData` 一次给全。embed 整体升到 v4 前端时删掉这段。
- 本仓库作者的数据不会触发（没有跨应用同 id 的供应商）。按「以本机数据为由省略上游逻辑必须记待办」的规矩，照样跟进。

## 测试
- 全量 **173 用例绿**（163 → 173）；App target Release 编译通过；embed `tsc` 0 错误，产物两次重建逐字节一致。
- 先红后绿：桩代码（只加接口、行为不变）下新增的 10 个用例 9 红 1 绿，绿的那个是 `testOldCCSwitchKeepsFiveMinuteRate`，它断言的本就是旧行为。去重过滤改按 schema 生成那一步，旧用例全绿。
- TanStack 机制实测：用 clone 里的 query-core 5.90.3 起一个 `QueryObserver`，`setQueryDefaults` 给的 `select` 生效，两行 key 唯一、名称不变。
- **变异测试 22/22 被杀**：计价开关 4（门槛写成 4.0.6 / 4.0.8、按字符串比版本、读不到版本退回 5 分钟价）、成本拆分 5（倍数写成 2 / 1.25、开关关着仍拆分、去掉上限 / 下限钳制）、读版本号 2（改用 `Bundle(url:)`、只看第一个路径）、叠加层 4（不读 1 小时字段、把 5 分钟字段当 1 小时、口径只判一次、口径变了不清空）、去重分支 4（缺这条分支、不看 semantics、不限 codex_session、旧库也带分支）、Provider 行身份 3（appType 读错列、overlay 只按 id 分组、并入时只比 id）。
- **顺带修了一个测试夹具 bug**：第一轮「旧库也带分支」存活，查下来是 `Fixture.makeLegacyDB` 从没删掉过 `input_token_semantics` 列。`schema` 是多行字符串，收尾 `"""` 缩进 4 格，每行前导空格会被剥掉 4 个，列定义实际只缩进 2 格，而替换串写死了 6 个空格，所以「旧库」一直带着这一列，旧库降级路径从没被真正测到。改成按正则去列、删不干净直接报错之后：真旧库下全量用例仍全绿（降级路径本身没问题），该变异体被 `testLegacySchemaWithoutSemanticsColumnStillWorks` 杀掉。
- 已知缺口：`PanelWebView` 输出 `appType` 在 App 层，没有测试目标覆盖（App 层零测试的老问题，见待办「Shared 抽成 SwiftPM 包」）；embed 的 `select` 没有 JS 测试，靠 tsc、产物检查和上面的机制实测。

## 不跟 / 暂缓
不跟（逐条核过，与本仓库无关或已经一致）：
- #8045 显式 0 的 OpenAI 缓存字段（5667b287）：只改代理路径。两个 overlay 都不解析 OpenAI 格式，OMP 用自己的 usage 字段和自带成本。
- 额度可以显示「已用」（b7d548b6）：菜单栏码片本来就写「已用」，即上游新加的可选模式；告警线仍按剩余算（10-10 已对齐）。
- 会话日志扫描间隔（#8301）：overlay 本来就在每个刷新周期增量续读。
- Codex 会话压缩成 `.jsonl.zst`（v4.0.7）：`CodexQuota` 只读最新的 `.jsonl`。只有闲置 7 天以上的会话会被压缩，它们的额度窗口早已过了重置时间，读不到和归零没有实质区别。
- 导入侧的修复（Pi 速度估算 #8278、Codex 线程换模型 #8176、Codex 分叉 / 分页 #8213 / #8218、`cc-switch-official` 迁移）：数据经库进来，本仓库只读，不用跟。
- 表格左对齐（cb3c9fef）、深色模式文字调暗（3784fd9e）、统计表首字列（a0dd3b39 前端部分）：都是 v4 前端改动，embed 仍钉在 3.x。

暂缓：
- **embed 整体升 v4 前端**：评估同 10-10（M 级）。上游 5 天发了 6 个补丁版本，仍未稳定。
- 用户升到 v4 后（低）：会话行带估算 latency（v4.0.x）和估算首字时间（a0dd3b39），overlay 行恒为 0 / NULL，会拉低 Provider 平均延迟；3.x embed 不显示首字。
