## 3. 倍率为 0 的行（我们自己的口径 bug）
### 根因
- 汇总侧 `costL` 的倍率写的是 `COALESCE(NULLIF(CAST(l.cost_multiplier AS REAL), 0), 1.0)`；请求日志侧 `backfilledCosts` 写的是 `multiplier == 0 ? 1.0 : multiplier`。两处都把「倍率 0」当成「1 倍」，倍率为 0 的零成本行会被内置表按全价补上。
- 上游：倍率解析失败按 1 倍；解析出 0 就是免费，总价本来就是 0（v4.0.36 `b044f4b0` 明确跳过这种行的补价）。v4.0.36 的「供应商费用倍率」表单允许填 0，这种行以后会出现。
- 更正：11-20 出清单时说「请求日志显示 0」不对，两处一样多算。
### 前人意图
- 07-25 加 `NULLIF` 是为了让解析不了的字符串（`CAST` 得 0）回落 1 倍，对齐上游「解析失败按 1」；但把真正的 0 也一起吞了。
### 改法
- 新增 `Pricing/CostMultiplier.swift`：一条规则两种写法——`value(_:)`（Swift）和 `sql(_:)`（SQLite 表达式）。只认 cc-switch 实际写入的十进制写法（以数字开头，只含数字和至多一个小数点），取它的值；其他（空串、带空格、正负号、科学计数）一律按 1 倍。
- 倍率为 0：SQL 侧补价 = 价格 × 0 = 0；请求日志侧不补价，原样显示库里的值（同上游跳过补价）。

## 4. 同价推理档合并统计（#8845）
### 上游语义
- `statistics_model(raw)`：`raw` 去掉推理档（`-minimal/-low/-medium/-high/-xhigh`，不分大小写）和已知的 tiered 后缀后得到候选基础模型；**变体的价**（完整候选链，含前缀匹配）与**基础模型的直接价**（只做精确匹配，不剥推理档）四项都相等时，归到基础模型；缺任何一方的价都不合并。
- 模型统计：各行按 `statistics_model` 归并后累加；首字中位数按合并后的全部样本重新取（不是平均各档的中位数）；排序 = 总成本降序、同成本按模型名升序。
- 模型筛选：选中的模型如果自己不会被合并到别处，筛选条件同时匹配「模型名 + 会合并进来的后缀」（`SUBSTR` 取前缀精确比、余下部分小写后在后缀表里）；会被合并到别处的模型只做精确匹配。所有吃模型筛选的查询都生效（汇总、走势、供应商 / 模型统计、请求日志、最早日期）。
- 请求日志仍显示原始模型名。
### 模块设计
- `Pricing/ReasoningTiers.swift`（纯函数，不碰库）：`mergeTargets(_:)`、`statisticsModel(_:price:directPrice:)`、`mergedSuffixes(for:price:directPrice:)`。查价以闭包注入。
- `PricingTable.findDirect(_:)`：只做精确匹配，候选只走命名空间 / Desktop 前缀 / `-v<N>` / 点转横线 / 日期尾（对齐 `find_direct_model_pricing_row`）。
- `Usage/ModelMatch.swift`：一次查询里解析好的模型筛选（模型名 + 后缀表），出 SQL 条件（带绑定参数）和 Swift 侧的 `matches(_:)`（给叠加行用；按 Unicode 标量计长、只对 ASCII 转小写，与 SQLite 的 `SUBSTR` / `LOWER` 一致）。
- 查价来源：库里的 `model_pricing` 优先，查不到再用内置表（相当于上游那份总带着 seed 的库）。只在有模型筛选、或统计行里出现带档位后缀的模型时才读价格表。
- 依赖方向：`Usage → Pricing → ModelId`，无环。
### 改法（调用点）
- `scopeCondsL` / `scopeCondsR`（汇总、走势按日、统计、最早日期都经过它）、`requestLogs` 和 `trendHourly` 里各自手写的模型条件，统一改成 `ModelMatch` 出条件；顺手把这两处手写的条件换成 `scopeCondsL`（结果不变，对拍兜底）。
- `overlayRows` 的模型过滤改用 `ModelMatch.matches`。
- `modelStats`：SQL 行和叠加行都按 `statisticsModel` 归并；首字样本按归并后的键合并、重新排序再取中位数；最后按（成本降序、模型名升序）排序。

## 8. 额度接口限流时的退避与落盘（实施中追加，用户选方案 A）
### 现象
- 装上 v2.6.0 后菜单栏 Claude 组的 `7D` 码片只有标签、没有数值。
### 根因
- `api.anthropic.com/api/oauth/usage` 按账号限流（HTTP 429）：Claude Code 状态栏脚本先收到 429、被要求等 142 分钟；CC Usage 之后每 5 分钟一次 429（旧版 v2.5.0 已经如此，不是 v2.6.0 引入的）。这个接口实测一小时十几次就限流，CC Usage（每小时 12 次）加状态栏（每小时 6 次）本来就贴着上限，当天又多了几次重启（每次重启都立刻多查一次）。
- CC Usage 自身的两个短板：①不看 `Retry-After`，限流期间照旧每 5 分钟打一次，可能把限流拖长、同账号的状态栏也跟着拿不到数；②额度只存在内存里，重启后限流解除前码片一直是空的（额度为空时 `MenuBarLabel` 只画标签）。上游 cc-switch 同样不处理 `Retry-After`、同样只存内存。
### 前人意图
- 5 分钟节流照搬 cc-switch 的 REFETCH_INTERVAL；「闸门按上次发起查询的时刻推进，429 后自动退避 5 分钟」——当时以为 5 分钟够，没考虑服务端要求等更久。
### 改法
- `Shared/Quota/QuotaThrottle`（纯值类型）：平时间隔 5 分钟；429 按 `Retry-After` 暂停（没给先停 30 分钟、最长 6 小时）；手动刷新不受间隔限制，但受暂停限制。
- `Shared/Quota/RetryAfter`：解析整数秒或 HTTP 日期。
- `Shared/Quota/QuotaSnapshot`：落盘内容 = 上次成功的各档额度 + 闸门状态；过了重置时刻的档不显示。`QuotaTier` 加 `Codable`。
- `QuotaCache`：注入存储（App 用 UserDefaults `quota.claude.snapshot`）和时钟；发请求前就记下查询时刻并落盘；`QuotaStatus` 加 `.rateLimited(retryAfter:)`；`ClaudeUsageAPI.interpret` 把 HTTP 响应分类抽成纯函数。
- 5 分钟间隔不变（对齐上游）。
