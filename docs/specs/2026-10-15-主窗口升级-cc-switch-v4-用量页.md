# [TECHNICAL SPECIFICATION] 主窗口升级到 cc-switch v4.0.12 用量页（只读精简版）

## 变更背景
- cc-switch 4.0 把用量页整体重做（v4.0.4 正式版，v4.0.12 为本轮基准 `51ac86f1`），包括：页头 + 筛选行（应用图标、带次数的供应商 / 模型下拉、含「全部」的日期范围）、新指标卡、53 周热力图、带状态码筛选和翻页的请求日志、多了成功率 / 速度 / 首字三列的供应商和模型表、请求详情抽屉。
- 主窗口此前一直钉在 3.20.3+14（`fdbe3a85`）的前端上。10-10 评估过整体升级（M 级），当时因上游 5 天连发 6 个补丁暂缓；用户 10-15 已把本机 cc-switch 升到 v4.0.12，要求跟进。
- 动手前和用户逐项定下的取舍（全部选了推荐项）：
  1. 热力图常驻在走势图下方（沿用 10-10 的选择）；选「全部」时只显示热力图，不和走势图重复。
  2. 不放「定价」页签（改价、models.dev 同步都是写操作）。
  3. 页头右侧保留 CC Usage 自己的刷新间隔（关 / 5 / 10 / 30 / 60 秒，默认 5 秒，和菜单栏联动），只换成 v4 样式；不要 v4 的「立即同步 + 扫描间隔」。
  4. 还没被 cc-switch 导入的叠加行，速度和首字显示「—」，不在 CC Usage 里另做估算。

## 设计要点

### 1. embed：v4 用量页的只读精简版
- 布局：顶部 46pt 留白（原生拖动条和红绿灯在这里，网页控件放进来点不到）→ v4 `AppPageHeader`（标题 + 说明；右侧刷新间隔 + 官方额度徽标）→ v4 筛选行 → 可滚动的内容区（指标卡 → 走势图 → 热力图 → 子页签）→ 请求详情抽屉。
- 去掉的写操作：立即同步（`sync_session_usage`）、数据来源抽屉（自动扫描开关、路由日志、重建 Codex）、定价页签（改价、models.dev 同步）、空状态里的「配置定价」。数据来源抽屉里其余内容都是 cc-switch 自己的控制项，整个不放。
- 刷新：v4 的子组件都传 `refreshIntervalMs=0`、不各自轮询，由 `useUsageAutoRefresh` 扫会话日志、再靠后端事件刷新。CC Usage 不写库、没有那个事件，所以改成自己的 `useEmbedAutoRefresh`：按刷新间隔统一 `invalidateQueries(usageKeys.all)`（原生每次查询都会顺带续读叠加层），窗口不可见时暂停、重新可见时补一次。「关」就是不自动刷新。
- 根节点照 v4 `main.tsx` 套 `ThemeProvider`（固定深色，独立的 storageKey）、`MotionConfig`、`TooltipProvider`、`Toaster`；`body` 挂 `is-mac`；语言固定英文（与用户 cc-switch 的设置一致）。
- 以前为钉住的 3.x 组件打的补丁都删了：`keepPreviousData` 的 `setQueryDefaults`（v4 hooks 自带）、provider-stats 的 `select` 组合键（v4 表格本来就按 `[appType, providerId]` 作 key）、`APP_FILTER_ICON`（v4 用 `AppGlyph`）。
- 详情抽屉是 Radix Dialog（`role="dialog"`、`fixed inset-y-0`），默认从窗口最顶上开始，右上角的关闭按钮会落在原生拖动条下面点不到；`index-embed.html` 用 `top: 46px !important` 把它压到拖动条下面。
- **只让内容区滚**（用户试用时报的 bug）：表格里的 `sr-only` 文字是 `position: absolute`，内容区没有定位时它们以整页为参照，逃出内容区的滚动裁剪、把整个文档撑高（一页 20 行就多出几百像素），于是出现第二层滚动条：外层一滚，页头和筛选行跑出窗口、底下一大片空白。修法：内容区加 `relative`（治本）；`html` / `body` / `#root` 固定为窗口高度且 `overflow: hidden`（兜底：以后再有元素逃出来也只会被裁掉）。无头 Chrome 量出文档高度从 919 回到 726（= 视口），内容区照常滚动。

### 2. Provider / Model 统计：并入 rollup，补成功率、速度、首字（对齐 v4.0.12 usage_stats.rs）
- **并入整日 rollup**：明细子查询与 `usage_daily_rollups` 子查询 UNION ALL 后再按 (provider_id, app_type) / 有效计价模型汇总，日期边界复用 `rollupDateBounds`（与 Hero 同一套整日规则）。以前两张表只读明细（顶部说明里写的「与 Hero 同源」并不成立：Hero 一直并 rollup），区间跨到 30 天前时各行之和比顶部总数少一截；v4 加了「全部」范围后差得更明显。真实库验证：近 7 天、全部两种范围下，Provider 行之和与 Model 行之和都等于 Hero 请求数。
- **成功率**：(成功数 / 请求数) × 100，rollup 的 `success_count` 一并计入。模型表的 `successRate` 是 v4 前端的必填字段。
- **速度**：四个累计字段逐字对齐上游的资格条件，两组分开累计，前端自己除：
  - 精确：路由记的行（`data_source = 'proxy'`）、有首字、输出 ≥ 100、生成窗口（耗时 − 首字）≥ 100ms；累计输出与生成窗口。
  - 估算：会话日志导入的行（`data_source <> 'proxy'`）、输出 ≥ 200、耗时 ≥ 1s；累计输出与整段耗时（含首字等待，不减推出来的首字）。
  - rollup 没有逐条计时，不计入速度。
- **首字中位数**：另起两条查询（与主查询同一套明细 WHERE），按键、值排好序取出，在 Swift 里算中位数：奇数个取中间，偶数个取中间两个的整除平均。精确首字取路由的成功行，估算首字取会话日志导入、推出了首字的行。Provider 的分组键是 `provider_id || char(31) || app_type`（与主查询的行身份一致），Model 的是有效计价模型。
- **耗时均值**：(明细耗时之和 + rollup `avg_latency_ms × request_count` 之和) / 总请求数，整除（同上游）。v4 表格已不显示这一列，保留是为了接口完整。
- **叠加行**：恒成功、没有计时，计入请求数、Tokens、成本、成功率，不进速度与首字（界面显示「—」，cc-switch 导入后自然出现），耗时按 0 折算（原有行为）。
- 成本仍用 `costL` / `costR`（内置定价兜底），与上游的唯一有意偏差不变。

## 测试

## 暂缓 / 不做
- 定价页签、数据来源抽屉、立即同步：用户选择不放（见变更背景）。
- 叠加行的耗时 / 首字估算：用户选择显示「—」。cc-switch 挂在托盘时每 10 分钟导入一次，空白只持续到下次导入。
- README 主窗口截图仍是 7 月的 3.x 界面，待用户决定是否更换（新截图会带真实用量数字）。
