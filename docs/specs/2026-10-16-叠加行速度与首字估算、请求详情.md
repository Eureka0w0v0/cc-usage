# [TECHNICAL SPECIFICATION] 叠加行的速度与首字估算、请求详情抽屉

## 变更背景
- 用户反馈：主窗口请求日志的 Speed / First token 两列「很多时候都出不来」，一整页都是「—」。
- 根因（真实库复现）：「—」的行都是 cc-switch 还没导入、由 CC Usage 自己从会话日志叠加出来的行。叠加层从来不算计时——`requestLogs` 把叠加行写死成 `latencyMs: 0`、`firstTokenMs: nil`；`SessionOverlay` 只解析带 `usage` 的行，不建对话链（uuid → parentUuid），推不出请求起点。前端 `format.ts` 拿到 0 / 空就显示「—」。
- 10-15 定「叠加行显示—」的前提是「cc-switch 挂在托盘、每 10 分钟导入一次，空白最多持续 10 分钟」。用户的 cc-switch 关了开机自启、平时不在后台，空白会一直持续到下次打开它；用户上一次同步之后的一整天，请求日志第一页全是「—」。
- OMP 的行更糟：cc-switch 永远不导入 OMP，CC Usage 是唯一来源，也恒为「—」。OMP 日志其实每条回复都带客户端实测的 `duration` / `ttft`（本机几乎全部回复都有）。
- 排查中顺带发现：原生桥没有实现 `get_request_detail`（落到 `default` 返回 null），真机上点任何一条请求，详情抽屉都是「Request not found」——10-15 只在浏览器 mock 里验过。
- 和用户确认的方案（都选了推荐项）：
  1. 推翻 10-15 的约定：叠加行按上游 v4.0.12 的规则估耗时和首字；
  2. 请求详情一起修；
  3. 收尾只构建并装到 /Applications，提交和发版等用户看过再说。

## 设计要点

### 1. Claude 叠加行：逐条移植上游的估算（v4.0.12 a0dd3b39 / 7e9b99bc / b0b6559a）
- **起点**：从回复第一块的父行往上找，跳过 `attachment`（时间戳不可靠），最多 32 跳，取第一个别的行（用户消息、工具结果、重试的 system 行）的时间戳。
- **耗时** = 各块写完时刻里最晚的 − 起点，落在 [100ms, 1h] 之外不要。只给这一段读到的代表行带 `stop_reason`、且看得到第一块（`apiBlockIndex` 为整数 0 或缺省）的回复算。
- **首字**：第一块是思考块（`content[0].type == "thinking"`、`thinkingDurationMs > 0`）时 = 块写完时刻 − `thinkingDurationMs` − 起点，必须落在 (0, 耗时]。
- **回看窗口**：起点行常在 cc-switch 游标之前（工具结果先落盘，回复整条结束才写），从 db 游标起读时先读游标前最多 256KB（上游 `CHAIN_SEED_BYTES`），只记链和块计时、不计用量；窗口不从文件头开始时丢掉第一段半行。旧行号游标（A/B 态）首读被跳过的行与上游一样不记链。
- **合并规则**（上游 `refresh_session_log_entry_on_conn`）：后面的块到了，耗时取大、首字先到先得、这一轮估不出来原样保留；行被输出更大的块替换时带上先前的计时。
- **对话链跨轮保留**：叠加层每个刷新 tick（默认 5 秒）都续读，起点行（常是带截图的工具结果，单行几百 KB 到几 MB）上一轮读走、回复这一轮才到是常态。最初的实现每轮重建对话链、只靠 256KB 回看，回看窗口会落在大行中间、找不到起点——真机上用 computer-use 截图后的几条请求全是「—」，用真实日志逐 tick 回放也复现了（每轮重建时有一批行丢计时）。改为每个文件一份 tracker，存在续读进度里，续读时接着往里加，db 游标推进、文件被重写或消失时随进度一起重建：等于「从游标一次读到现在」，与 cc-switch 隔一阵一次性导入时看到的相同，续读也不再每轮重复解析回看窗口。内存随未入库的行数增长（每行约百字节）；取出来续读前先放掉进度里那份引用，避免每加一行都整份写时复制。
- 数字判定照 serde_json：`thinkingDurationMs` / `apiBlockIndex` 只认整数（布尔、小数、null 都不算）；时间戳按 chrono 的 RFC3339 规则解析到毫秒。
- 考虑过不做：新版 Claude Code 日志的 `api-request` 行能给出更准的请求起点，但上游没用，用了入库前后数字会跳。

### 2. 对话链行的快扫
- 建链要把不带 usage 的行（用户消息、工具结果、attachment）也读进来，这些行占日志字节的大头，整行 JSONSerialization 让冷启动全量重扫慢了一倍。
- 只用得到顶层四个字段（uuid / parentUuid / timestamp / type），于是只走顶层对象：字符串按转义找收尾引号（memchr + 反斜杠奇偶），对象和数组按深度整段跳过，不建对象。
- 只在有把握时给结果，否则 `.needsFullParse` 交回整行解析：键或要取的值带转义、assistant 行（还要记块计时）、结构不完整、顶层不是对象或后面还有字符。同名键后出现的覆盖先出现的，非字符串值等于没有（与整行解析成字典、上游 `as_str` 一致）。
- 本机全部会话日志里的对话链行与整行解析逐行对拍零差异，快 35 倍。

### 3. OMP 叠加行
- OMP 每条回复自带客户端实测的 `duration`（开始到结束，含首字等待）和 `ttft`，单位毫秒、带小数：四舍五入后直接采用，合理范围同上（耗时 [100ms, 1h]，首字 (0, 耗时]），没有耗时就不给首字。cc-switch 不导入 OMP，没有上游口径可对。
- 前端把非路由来源一律当估算值，OMP 的值同样带 ≈、速度按整段耗时算。

### 4. 统计表、请求日志、请求详情
- **Providers / Models**：叠加行按行身份先汇总，再在读 SQL 结果时逐行并入（原来是事后 `firstIndex` 查找）。够门槛的（输出 ≥ 200、耗时 ≥ 1s，同 `speedEstimateEligibleL`）进估算速度；推出了首字的与库内样本合在一起再取中位数（`firstTokenMedians` 改为 `firstTokenSamples` 返回样本）；平均耗时 = (库内耗时和 + 叠加行耗时和) / 总请求数，整除（原来叠加行按 0 折算，会拉低）。成功率改按整数计数合并，结果不变。
- **请求日志**：叠加行带上 `latencyMs` / `firstTokenMs`。
- **请求详情**（对齐 `get_request_detail`）：按 `request_id` 直查明细，成本照列表补算，不套跨源去重（上游同样不套）；库里没有就找叠加行；都没有回 null。查询出错抛 `UsageStoreError.step`，前端显示可重试的错误，而不是「Request not found」。
- **顺手的整理**（只搬代码、不改行为）：`SessionOverlay.scanFileLocked` 拆成定读取计划（`readPlanLocked`）、读文件尾（`readTailLocked`）、逐行消费（`consumeLocked` / `consumeLineLocked`）；`ingestLocked` 的成本计算提成 `costs`；OMP 的时间戳回落提成 `createdAt`；`readRequestLogRow` 的成本补算提成 `requestLogCosts`，按名取列收成 `RequestLogColumns` 两处共用。`requestLogs` / `providerStats` / `modelStats` 仍超过 50 行（SQL 文本占大头，均比改动前短），OMP 的 `scanFileLocked` 没动。
- **读文件失败不再空吞**：原来 `try? seek` 失败会悄悄从文件头读（偏移错位，可能把已消化的行再算一遍），`try? readToEnd` 失败会把文件当成读完了。现在定位或读取失败都不动进度、下一轮重试，日志每个文件只记一次（`Logger` category `overlay`）。

## 测试
- 全量 **223 用例绿**（178 → 223），新代码零警告；App target Release 构建零警告。
- 先红后绿：只加 `OverlayRow` 两个字段（值恒 0 / nil）时，叠加层、OMP、统计表、请求日志四组新用例全红，旧用例全绿；新纯函数（RFC3339、合并规则、快扫）和请求详情的用例由变异测试证明有效。
- 上游 `session_usage.rs` 的 7 个计时用例逐条移植到叠加层，日志行、时间戳、断言值与上游一致；另有 1 小时上限、32 跳、256KB 回看边界、旧行号游标、行被替换保留计时、块时间戳缺失或乱序、非整数 `apiBlockIndex`、回落整行解析、起点大行在上一轮读走等本仓用例。
- 变异测试四轮共 **100 个，全部被杀**：第一轮 67 个（合理范围各边界、合并规则、回看大小、跳数、attachment 跳过、第一块 / 思考块判定、RFC3339 各条规则、OMP 映射、统计表各处并入、详情回落与去重）；第二轮 18 个（快扫的转义、奇偶、深度、同名键、结尾检查、回落路径，以及两处接入点）；第三轮 4 个（对话链不跨轮保留、保存时丢掉、回看字节算进已读进度、不回看）；第四轮 11 个，是整理之后对扫描、成本、时间戳、成本补算的重放与补充——其中「补算时倍率写死 1」第一次存活，这是原有代码就有的测试缺口（列表 / 详情的成本补算从没测过倍率），补了 `testBackfilledRequestLogAppliesCostMultiplier` 后被杀。第一轮的判定脚本误把断言失败当成编译错误，按失败用例名重判后全部有效。
- 金标准对拍：cc-switch v4.0.12 一次性导入的一整批会话行（导入前一天多没同步），复制一份库删掉这批行和对应游标，让叠加层从头重算——耗时、首字、输出 token 逐条与 cc-switch 自己写的完全一致。
- OMP：本机全部 OMP 回复，`OmpOverlay` 给的耗时 / 首字与按原始字段直接算的逐条一致。
- 逐 tick 回放：几个真实的大会话文件（含带截图的会话）按随机块大小逐段追加、每段续读一次，最后与一次读完逐行对比：跨轮保留后完全一致；改之前（每轮重建对话链）有一批起点为大行的请求丢了计时。
- 真机：装到 /Applications 后，请求日志里还没入库的行带上 ≈ 速度和首字；新版运行中逐 tick 读到的、起点是截图大行的请求同样有值；点任一行，详情抽屉正常显示，Performance 一节有估算速度、首字、耗时。
- 性能（冷启动全量重扫几百 MB 日志的极端情形）：改动前 1.0s → 只加整行解析 2.0s → 加快扫后约 1.25s；峰值常驻内存只多约 3MB。日常只读游标之后的增量，量小得多，都在后台线程。

## 暂缓 / 不做
- 上游的展示门槛不改：输出不到 200 token 的回复不估速度、不以思考块开头的回复没有首字，cc-switch 自己也显示「—」；改了会和 cc-switch 对不上。
- 回复还没写完（没有 `stop_reason`）时不估，写完后的下一轮才有值（同上游）。
- 快扫与整行解析只对合法 JSON 保证一致；含孤立代理对等 serde_json 会拒收的行，整行解析和快扫都可能与上游不同（只影响入库前的显示，入库后以库为准）。
- App 层（`PanelWebView` 的 `get_request_detail`）仍没有测试目标覆盖，靠真机验证。
